# AGENTS.md - Drupal CMS

This file scopes agent rules to the `drupal-cms/` component only.
For the Python application rules see the root `AGENTS.md`.

## Overview

The `drupal-cms/` directory contains a Drupal CMS recipe system. It is a
separate component from the Python application. All work here is PHP-based
and requires DDEV for local development. Python tooling (Pylint, mypy,
Pylance) does not apply here.

---

## Critical Rules (Non-Negotiable)

### 1. NO Emojis - NEVER

Never use emojis in any `.php`, `.twig`, `.yml`, or `.md` files in this
directory. This is a hard requirement shared with the rest of the project.

### 2. DDEV Is Always Required

All commands that interact with the Drupal installation, Composer, Drush,
or any infrastructure (Milvus, Solr, etc.) must be prefixed with `ddev`.
Never run these commands bare on the host machine.

```bash
# Start the environment first
ddev start

# Composer
ddev composer install
ddev composer require drupal/some_module
ddev composer update

# Drush
ddev drush cr
ddev drush updb
ddev drush cex
ddev drush cim

# Infrastructure services (Milvus, Solr, etc.)
ddev exec <command>
```

After making structural changes you may need to rebuild:

```bash
ddev rebuild
```

### 3. PHP Code Quality Standards

All custom PHP code in `web/modules/custom/` and `web/themes/custom/`
must pass both quality tools before committing.

**PHPCS with Drupal coding standard:**

```bash
ddev exec vendor/bin/phpcs --standard=Drupal,DrupalPractice \
  web/modules/custom web/themes/custom
```

**PHPStan at minimum level 6:**

```bash
ddev exec vendor/bin/phpstan analyse \
  --level=6 \
  web/modules/custom web/themes/custom
```

Rules:

- Never use `// phpcs:ignore` or `// phpstan-ignore` unless absolutely
  unavoidable; always fix the underlying issue instead.
- PHPStan level 6 enforces strict null checks and type inference. Add
  proper type hints and null guards rather than suppressing errors.
- Drupal coding standard requires proper docblocks for all hook
  implementations and public methods.

### 4. Drupal Contrib Patch Policy

Never leave direct edits in `web/modules/contrib/` as the only
implementation. If a contrib module requires a fix:

1. Create a patch file in `patches/`.
2. Register the patch in `composer.json` under `extra.patches`.
3. Enable and use Composer patch tooling so the fix reapplies after updates.

This keeps contrib upgrades reproducible and prevents local hotfixes from
being lost on reinstall or update.

### 5. Documentation Must Track Code

| Change Type | Documentation to Update |
|-------------|------------------------|
| New custom module | this AGENTS.md, relevant `docs/` file if integration-facing |
| New DDEV service | this AGENTS.md infrastructure section |
| Changed infrastructure (Milvus, Solr, etc.) | root `docs/` integration docs |

## DDEV Infrastructure Services

| Service | Config file | Host port | Purpose |
|---------|-------------|-----------|---------|
| Solr | `docker-compose.solr.yaml` | 8983 | Drupal Search API full-text index |
| Milvus | `docker-compose.milvus.yaml` | 19530 | Vector DB for Python semantic search |

Both start automatically with `ddev start`.

Milvus takes up to 90 seconds to become healthy on first start. Verify with:

```bash
ddev milvus-status
```

### Ollama runs on the host, not in DDEV

Ollama is **not** a DDEV service. The Dockerised one was removed (no GPU
passthrough, duplicated the host install); see the comment in
`docker-compose.host-gateway.yaml`. Drupal reaches the host Ollama on
`host.docker.internal:11434`, which that same file wires up via
`extra_hosts: host-gateway`.

This only works if the host Ollama listens on an address the container can
reach. The default `127.0.0.1:11434` is **not** reachable - containers arrive
via the docker0 gateway (172.17.0.1) with a source address in
`172.16.0.0/12`, and get connection refused. The symptom is
`cURL error 7: Failed to connect to host.docker.internal port 11434` in
watchdog under type `ai`, with `ai_search` indexes stalling part-way through
because embeddings fail.

Check the bind address and reachability with:

```bash
ss -ltnp | grep 11434                       # expect 0.0.0.0:11434
ddev exec "curl -s -o /dev/null -w '%{http_code}' \
  http://host.docker.internal:11434/api/tags"
```

If it is bound to loopback only, set `OLLAMA_HOST=0.0.0.0:11434` in a systemd
override at `/etc/systemd/system/ollama.service.d/override.conf` and firewall
port 11434 to `172.16.0.0/12`.

### Solr configset

The Solr core config lives in `.ddev/solr-core/conf/` and is mounted into the
Solr container by `docker-compose.solr-modules.yaml`, which also sets
`SOLR_MODULES=extraction,langid,ltr,analysis-extras`.

The configset is generated by `search_api_solr` and is version-stamped
(`<schema name="drupal-<module-version>-solr-9.x-0">`). **After updating
`drupal/search_api_solr`, regenerate and reinstall it**, otherwise the Solr
server runs a configset from the previous module version:

```bash
ddev drush solr-gsc solr /tmp/solr_config.zip
ddev exec "mkdir -p /tmp/solrconf && cd /tmp/solrconf && \
  unzip -o -q /tmp/solr_config.zip"
ddev exec "cp -f /tmp/solrconf/* /var/www/html/.ddev/solr-core/conf/"
ddev drush solr-reload solr
ddev drush search-api:index solr_content
```

`search_api_solr` emits a standing warning about deprecated `lib` directives on
Solr 9.8+. It is unconditional for that Solr version and does not indicate a
problem here - `SOLR_MODULES` is already set.

### Orphaned media files

`file.settings: make_unused_managed_files_temporary` is set to **true** here,
against Drupal's default. With core's default (`false`) a file whose usage
count drops to zero stays `status = 1` (permanent) forever, and cron's file
garbage collector only ever deletes `status = 0` (temporary) files older than
`temporary_maximum_age`. The result is that deleting a media entity removes the
entity but leaves the image on disk indefinitely - regenerating portraits
accumulated 25 orphans / 12.8 MB before this was turned on.

Find orphans with:

```bash
ddev drush php:eval 'echo \Drupal::database()->query(
  "SELECT COUNT(*) FROM {file_managed} f
   LEFT JOIN {file_usage} u ON f.fid = u.fid WHERE u.fid IS NULL")->fetchField();'
```

Note `public://media-icons/generic/*` and `public://login-wallpaper.png` are
shipped by core and the install profile; they are legitimately absent from
`file_managed` and are not orphans.

### Settings file protection

Drupal's status report flags writable `settings.php` / `services.yml` as a
security risk, but DDEV's settings management makes them writable again every
time it regenerates `settings.ddev.php`. The `post-start` hook in
`.ddev/config.yaml` runs `.ddev/scripts/protect-settings.sh`, which restores
mode `0444` on `settings.php`, `services.yml`, and `settings.local.php` after
every start. Do not remove the hook to "fix" a permissions error - unprotect
the file for the duration of the edit instead:

```bash
chmod 644 web/sites/default/settings.php   # edit
chmod 444 web/sites/default/settings.php   # re-protect
```

Entity-deletion locking is **not** a custom module here - it is contrib
`drupal/lock_entity`, tracked against the `1.0.x-dev` branch (no tagged
release yet). Update it with
`ddev composer update drupal/lock_entity --with-all-dependencies`.

Its tests extend `Drupal\Tests\UnitTestCase` / `KernelTestBase`, which this
project cannot currently run - `drupal/core-dev` is not installed, and the
PHPUnit present (12.x) is newer than the `PhpUnit11` compatibility shim core
11.4 ships. Running them needs
`ddev composer require --dev drupal/core-dev --update-with-all-dependencies`.

### dnd_content

GraphQL mutations for content creation, plus the **wiki cache** surface backing
the Python RAG system:

| Operation | Kind | Purpose |
|-----------|------|---------|
| `wikiCacheEntry(urlHash)` | Query | Read a cached page; NULL is a miss |
| `wikiCacheCount` | Query | Entry count, for cache statistics |
| `setWikiCacheEntry(...)` | Mutation | Create or replace an entry |
| `deleteWikiCacheEntry(urlHash)` | Mutation | Remove an entry; TRUE when absent |

Entries are keyed by the MD5 hash of the page URL, stored as the node title.
`wiki_cache` is **deliberately not exposed through graphql_compose** - these are
internal cache rows and Gatsby must never source them. Writes require the
`create` / `edit any` / `delete any wiki_cache content` permissions on the
`gatsby_user` role.

Both read resolvers add the `node_list:wiki_cache` cache tag. Without it the
GraphQL result cache holds a lookup **miss** indefinitely and the cache can
never warm up - the tag is what lets a later write invalidate an earlier miss.
Any new resolver reading entity data needs equivalent cache metadata.

**Mutations validate only the fields they set.** `UpdateCharacter` uses
`$violations->getByFields($changed)` after `$node->validate()`. Validating the
whole node lets unrelated pre-existing damage - a dangling
`field_equipment_items` reference to a deleted item, say - block every edit to
that character. Note `getByFields()` keeps only the named fields;
`filterByFields()` does the opposite and *removes* them.

### dnd_migrate

Provides Drupal migrate source and process plugins for importing the project's
JSON game data (characters, NPCs, items) into Drupal content nodes.

**Plugins provided:**

| Plugin type | ID | Description |
|-------------|-----|-------------|
| Source | `dnd_json_directory` | Reads all `*.json` files from a directory; one row per file |
| Source | `dnd_items_json` | Reads a keyed-object JSON file (custom_items.json); one row per key |
| Source | `dnd_spell_slots_source` | Flattens spell_slots objects into one row per (character, slot_level) |
| Process | `dnd_join_array` | Joins a PHP array into a single string with a configurable separator |
| Process | `dnd_spell_slot_lookup` | Resolves spell_slots to paragraph entity_reference_revisions values |

**Migration IDs and run order:**

1. `dnd_items` - item nodes from `game_data/items/custom_items.json`
2. `dnd_npc_nodes` - NPC nodes from `game_data/npcs/*.json`
3. `dnd_character_backstory` - paragraph:wysiwyg entities for character backstories
4. `dnd_character_spell_slots` - paragraph:spell_slot entities per slot level
5. `dnd_character_nodes` - character nodes from `game_data/characters/*.json`

**Running migrations:**

Enable the module and run with Drush:

```bash
# Enable the module
ddev drush en dnd_migrate

# Run all D&D migrations in dependency order
ddev drush migrate:import --group=dnd --execute-dependencies

# Run a single migration
ddev drush migrate:import dnd_items

# Check migration status
ddev drush migrate:status --group=dnd

# Roll back (removes Drupal content, does not touch source JSON)
ddev drush migrate:rollback --group=dnd
```

**Source path configuration:**

The `data_dir` and `file_path` values in each migration YAML default to DDEV
container paths (`/var/www/html/game_data/...`). If the project is mounted at a
different path, update those values in each migration's `source:` block.
